# SimCity 4 .UI Layout Scripts — Extraction & Format Analysis (2026-07-21)

Companion to `..\dbpf\NOTES.md` (UI image art, type 0x856DDBAC). This covers the
**layout scripts** that bind windows to that art.

## Where they live

- **TypeID: `0x00000000`** in `SimCity_1.dat` (none in SimCity_2..5, EP1, or Locale
  were checked here — SimCity_1 is where the base UI lives, same as the art).
- 330 entries, all QFS/RefPack-compressed except 42. Extracted with the verified tool:

  ```
  ..\dbpf\DbpfExtract.exe "C:\Program Files (x86)\Steam\steamapps\common\SimCity 4 Deluxe\SimCity_1.dat" extracted 0x00000000
  ```

  330/330 extracted, 0 failures → `extracted\` (renamed `.png` → `.ui`;
  `extract-manifest.csv` has the full TGI list).

### Census by group

| Group | Count | Content |
|---|---|---|
| `0x96a006b0` | 271 | **GZWin layout scripts** — the default (1024x768+) layouts. Text. |
| `0x08000600` | 10 | **800x600 layout overrides** for 10 screens (group ID literally encodes the resolution: 0800 x 0600). Same instance IDs and same window IDs as their 96a006b0 twins, different pixel geometry. |
| `0x8a5971c5` | 48 | 44 binary `AB..`/`AE..` blobs (animation-bank payloads sharing type 0 — **not** layouts) + 4 INI-style config texts (network/terrain/audio params, EP feature flags). |
| `0x4a87bfe8` | 1 | INI-style config text. |

So the layout-script corpus proper = **281 text files**: `# Generated by UI editor`
header + pseudo-XML GZWin markup. The community-cited candidate group `0x8a5971c5`
is a red herring for layouts — under type 0 it holds animation blobs and INI configs.

## Format

Text, one pseudo-XML element per line, nested via `<CHILDREN>...</CHILDREN>` blocks.
Every control is a `<LEGACY ...>` tag whose `clsid` selects the control class
(`GZWinGen`, `GZWinBtn`, `GZWinBMP`, `GZWinText`, `GZWinFlatRect`, `GZWinSlider`,
`GZWinTextEdit`, ... plus raw hex clsids for custom classes, e.g. `0x89e1567c`
toolbar container, `0xc7a0e17e` demand-bar host).

Annotated real example (trimmed from the save/quit dialog, `I-0a55161d`):

```
# Generated by UI editor
<LEGACY clsid=GZWinGen iid=IGZWinGen id=0xaa921f4f     ← window ID (what the engine + our hooks look up)
        area=(332,232,662,389)                          ← PIXELS, (x1,y1,x2,y2); absolute for roots, parent-relative for children
        image={46a006b0,144161e4}                       ← art = {GroupID, InstanceID}; type 0x856DDBAC implied
        blttype=edge                                    ← draw mode: edge | tiled | normal
        gutters=(64,64)                                 ← client padding (NOT slice insets — see below)
        winflag_visible=yes ... titlebar=no fill=yes >
<CHILDREN>
   <LEGACY clsid=GZWinBtn iid=IGZWinBtn id=0x8a921f5b
           area=(7,4,307,34)                            ← 300x30 button
           caption="Save and Quit" captionres={0a554ae8,ca6cd434}   ← inline text is a dev fallback; captionres/tipres = LTEXT resource ref
           image={46a006b0,144161eb}                    ← 120x30 strip = FOUR 30x30 state cells (normal/hilite/pressed/disabled)
           font=GenButton gutters=(0,0,0,0)             ← 4-tuple gutters on buttons (l,t,r,b padding)
           btnclicksnd={ca47efd9,4a5c31d7} >            ← sounds also referenced {group,instance}
</CHILDREN>
```

Attribute survey across all 281 layout files (full counts in scratch survey):
every control has `clsid`, `area`, `fillcolor`, 14 `winflag_*`; common extras are
`gutters` (4520), `image` (2962), `caption`/`captionres`, `font` (named styles only —
no sizes in scripts), `imagerect` (839), `edgeimage` (844), `blttype` (540),
`tiptext`/`tipres`, `textoffsets`, `tipoffsets`. **There is no inset/edges/corners/
slice attribute anywhere in the corpus.**

Key drawing attributes:

- `blttype=` (on GZWinGen-style windows): `edge` (277) | `tiled` (254) | `normal` (9).
- `edgeimage=yes|no` (on GZWinBMP, 56 yes / 788 no): edge-blt (9-slice-style) the
  source rect to fill the window instead of 1:1 blitting.
- `imagerect=(x1,y1,x2,y2)` (on GZWinBMP): **source sub-rectangle in image pixels**.
  Corner-format proof: the city HUD background `14015545` is 878x182 and a child at
  `area=(122,111,254,130)` uses `imagerect=(122,111,878,182)` — as (x,y,w,h) that
  would read 878px starting at x=122 of an 878px image, impossible; as corners it is
  exactly "same region of the big sheet, clipped by the window". (The SC4D/SimsWiki
  page guesses (x,y,width,height) — the corpus disproves that.)
- `gutters=` : 2-tuple on windows/text (client padding), 4-tuple on buttons. On
  `blttype=edge` dialog roots it is `(64,64)` in 271 of 277 cases while the frame
  art `144161e4` is only **78x78** — 64+64 > 78, so gutters cannot be the 9-slice
  inset; it is content padding (where children start).

### How art is actually used (patterns that matter for 2x)

1. **Big-sheet cropping**: one large PNG per screen (HUD = `14015545` 878x182,
   tool column = `14015546` 157x489) drawn 1:1 by the root BMP, then child BMPs
   re-crop regions of the *same* image via `imagerect` to layer text backgrounds.
2. **Multi-state sprite sheets**: e.g. mayor-rating bar `14015549` is 102x26 but
   `imagerect=(0,0,102,11)` picks the first 11px-tall state.
3. **Button state strips**: GZWinBtn image = 4 equal-width state cells. Verified
   exact: `14215e21` 256x50 for a 64x50 button, `14215e26` 192x38 for 48x38,
   `1401554c` 168x118 for 42x118. The generic dialog button `144161eb` 120x30 =
   four 30x30 cells stretched/edge-blitted to any button width (300x30 in dialogs).
   State selection divides the image width by 4 — proportional, no pixel constants
   in the script.
4. **Frame/9-slice art**: dialog frames `144161e4` (78x78) and `144161ee`/`14416240`
   (180x180) are edge-blitted (`blttype=edge` on windows, `edgeimage=yes` +
   `imagerect` source rect on BMPs) into arbitrary window sizes. **The corner/edge
   slice geometry appears nowhere in the scripts** — it is computed inside the
   runtime (GZWin) from the source image/rect. Community docs never decoded it
   either (the wiki entry for `edge` literally says "stretched?").

## Answers to the key questions

**(a) Are control sizes in pixels?** Yes — everything geometric is absolute pixels:
`area=(x1,y1,x2,y2)` (root = screen coords, children = parent-relative), `imagerect`,
`gutters`, `textoffsets`. There are no percentages, no anchors, no layout managers.
Fonts are named styles (`font=MayorPop`) with no sizes in the scripts. So yes:
a window (re)created by the engine comes back at **script-declared 1x size** —
consistent with our incremental re-scaling model, and it means any window the game
recreates mid-session reverts to 1x until our scaler touches it again. The engine
already ships per-resolution script sets (group `0x08000600` = 800x600 overrides of
10 screens, same window IDs, different pixel geometry) — precedent that "another
size = another copy of the numbers", not runtime layout.

**(b) How is art bound, and are draw modes declared?** Art is bound by
`image={GroupID,InstanceID}` — a 2-part reference with the type (0x856DDBAC)
implied; never a full TGI, never a filename. Both mirror art groups are used
(`46a006b0` 396 distinct refs, `1abe787d` 19, plus `22dec92d` 12 and 3 minor
groups) — this is why the art extraction found near-identical twins in both groups:
different scripts pick different groups for the same instance, so 2x art must
replace both (as `..\dbpf\NOTES.md` already concluded). Draw modes ARE declared:
`blttype=edge|tiled|normal` on windows, `edgeimage=yes|no` on BMPs, and `imagerect`
pixel source rects for sprite-sheet cropping. But **9-slice corner insets are NOT
declared** — edge-blt geometry lives in the GZWin runtime, derived from the source
image/rect.

**(c) Are image instances shared across screens?** Heavily. Of 423 distinct image
instances referenced by the 286 text files, **210 are referenced by 2+ script
files**; the generic button strip `144161eb` by 109 files, the 78x78 dialog frame
`144161e4` by 59, plus `144161e0`/`144161e2` (54 each) etc. City, region, options
and dialog screens all draw from the same pool. Any art swap is global — you cannot
2x one screen's art in isolation.

## Implications for the 2x art rollout

1. **The big one — `imagerect` is the blanket-2x breaker, not 9-slice insets.**
   Slice insets do not live in scripts (nothing to double there), but 839 `imagerect`
   crops DO, in absolute source pixels. Double the art and every sprite-sheet crop
   reads the wrong region at half scale: the HUD child panels crop quadrants of the
   doubled sheet, the mayor-rating bar picks 1.5 states instead of one, etc. Blanket
   2x art **requires** either (i) doubling the `imagerect` (and `area`) numbers in
   the scripts, or (ii) a runtime hook that scales source rects at draw time.
   Exception that survives untouched: GZWinBtn 4-state strips — state selection is
   width÷4, proportional, so doubled button strips still pick the right cell.
2. **Scripts are plain text and trivially patchable.** They QFS-decompress to
   editable text and `..\dbpf\DbpfPack.exe` can repack them; the game's own
   override chain (our `z_SC4UIScale_Art_2x.dat` mechanism) can ship modified
   copies at the same TGIs. Doubling `area=`, `imagerect=`, `gutters=`,
   `textoffsets=` in the live scripts is a regex-level transform. That makes
   "2x layout via patched scripts + 2x art" a viable complement (or alternative)
   to pure runtime window-scaling — and it fixes (a)'s recreate-at-1x divergence
   at the source. Fonts still need separate handling (named styles, defined
   elsewhere).
3. **Edge-blt behavior under 2x art must be verified in-game, not on paper.**
   Because slice geometry is runtime-derived from the source image, doubling frame
   art (78x78 → 156x156) with *unchanged* window sizes will draw corners at source
   thickness — visually doubled borders, overlapping on small controls (the dialog
   title strip is only 28px tall). If windows are doubled too (runtime scaling or
   patched scripts), proportional consistency is plausible but unproven. Test
   candidates: any `blttype=edge` dialog + an `edgeimage=yes` BMP frame.
4. **Only 10 screens have 800x600 variants** (group `0x08000600`); everything else
   has a single fixed-pixel layout. Whatever we do for 2x, those 10 instances exist
   twice and both copies matter only if 800x600 remains reachable — at our target
   resolutions the `96a006b0` set is the one the game uses.
