## The defect (what the user sees)

At 2x (probably all tiers >1x), some sub-flyouts — the second-level strip
that spawns off a first-level flyout button — attach the ring's connector
arm to the WRONG ROW of the strip, too high, and the strip's bottom items
are clipped. Confirmed wrong: **Sports Grounds** (5-item strip) and
**Plazas** (mayor column). Confirmed RIGHT: **Build Park** (11-item) and
**Green Spaces** (12-item), both in the build column.

The user's law, stated twice in layman's terms — treat it as the spec:

> "The bottom part of the flyout should be identical in all of these
> menus. Basically it should build from that bottom and fill in above it."

I.e. BOTTOM-ANCHOR: every sub-flyout's bottom edge at the same place; short
strips grow upward from it; the arm meets the strip near that shared bottom.

## What is actually known (all measured this session)

1. **The sweep path never fires.** The sweep-time formula sits behind the
   candidate-dock gate and that gate did not pass ONCE in a fully
   instrumented session (`SUBGEO BTN` count = 0). Containers are born
   already positioned by the birth hook (SUBBORNHOOK closes the first-paint
   window) and stay there. **Every pixel of sub-flyout placement comes from
   the birth path.** The sweep formula and the `kSubArmTargetBottom`
   calibration against it are dead code for placement. Do not tune them.

2. **The ring's auto offset is not `legT - tgtT`.** SUBSHIFT logged both:
   the formula was fed `autoY0 = legT - tgtT` (cnt=5: 123, cnt=11: 150)
   while the ring actually draws with `gSubRingAutoY` (cnt=5: 355, cnt=11:
   429) — a constant ~2.3-row gap. The birth hook sets
   `gSubRingAutoY = legDY - dy` (two writers, lines ~7196 and ~7212), a
   different quantity. Anything computing "the arm's true current row"
   must consume `gSubRingAutoY`.

3. **Birth-path numbers at 2x** (from SUBBORN2 + gSubRingAutoY):

   | menu | cnt | born nativeT | dy (final) | final top | height | bottom |
   |---|---|---|---|---|---|---|
   | Build Park (APPROVED) | 11 | 729 | −453 | 276 | 874 | **1150** |
   | Green Spaces (APPROVED) | 12 | 729 | −453 | 276 | 874 | **1150** |
   | Sports Grounds (WRONG) | 5 | 849 | −379 | 470 | 580 | 1050 |

   The approved menus' bottom is 1150; Sports Grounds' is 1050 — exactly
   the 100px "too high" the user sees. All cnt≥8 containers are 874 tall
   (8 rows × pitch 98 + 2×cap 50); only cnt<8 shrinks. `dy` includes the
   count-blind bornshift (232px up at 2x).

4. **Geometry constants (2x, identical for all counts):** ringH=53→106,
   capH=25→50, item 88, spacing 10, rowPitch 98, stripTop 50,
   ringBltY 239 (cnt=11) / 119 (cnt=5), SUBGEO2 AUTO 429 / 355.

## What was tried and failed (do NOT redo these)

- **StripShiftRows** (v4.0.27–30, RETIRED, law in
  `research/laws/project-sc4-flyout-never-shift-strip-independently.md`):
  shifting the strip child independently breaks bar+strip alignment. Never
  shift the strip; shift the container.
- **Sweep-formula tuning** (this session, v4.0.33–35): three rounds of
  dialling `kSubArmTargetBottom` (2.70→1.75→1.50) and swapping the formula's
  autoY input. Produced zero visible change because the sweep gate never
  fires (fact #1). The "Build Park is perfect" verdicts during this were
  actually the BIRTH path's output, coincidentally right.
- **Bottom-anchor at birth, first attempt** (v4.0.36, rolled back within
  the hour): computed the reference bottom as `SubPlaceTop(full8H,...) +
  full8H` and set `top = bottom − newH`. For 8-row menus this reproduces
  SubPlaceTop WITHOUT the 232px bornshift — so every approved menu dropped
  exactly 232px. Full regression, user ordered rollback, v4.0.35 restored.
  **The law was right; the constant was wrong.**

## The correct next move (as far as we know)

Bottom-anchor at birth, with the reference bottom taken from the APPROVED
chain, not from bare SubPlaceTop. Two equivalent formulations:

- **Formulation A (override the short-count delta only):** keep the birth
  path exactly as-is for cnt≥8 (it produces the approved 1150 bottom). For
  cnt<8, set `top = approvedBottom − newH` where `approvedBottom` is the
  bottom the same button's 8-row container would get:
  `approvedBottom = (nativeT + dy_model8 − bornshift) + full8H` with
  `dy_model8 = SubPlaceTop(full8H, cy, viewH, f) − nativeT` and
  `full8H = 2·RoundHalfUp(25f) + 8·RoundHalfUp(49f) − RoundHalfUp(5f)`
  (= 874 at 2x). Keep `gSubRingAutoY = legDY − dy` AFTER the override so
  the ring stays pinned to its button.
- **Formulation B (explicit constant):** `top = RoundHalfUp(287.5·f²) −
  newH` (1150 = 287.5·4). Simpler but hard-codes one machine's view height
  through the f² term; prefer A.

Predicted result at 2x: Build Park/Green Spaces pixel-identical (they ARE
the reference); Sports Grounds top 470→570 (+100 down, bottom 1150).

## Instrument cheat sheet

- `SUBBORN` (Info): full builder geometry at birth — cnt, pitch, stripTop,
  armRow(est), native CONT.
- `SUBBORN2`: birth scaling result incl. final (dx,dy). **dy here is the
  number that positions everything.**
- `SUBGEO2` (ungated, per open): container/ring/strip absolute rects +
  live AUTO (= gSubRingAutoY). The ring's true drawn position.
- `SUBSHIFT`: per-sweep formula inputs (both autoY variants, natRow,
  tgtRow, shift). Currently diagnostic-only (its output never applies).
- `SUBCAND`: the candidate gate dump. `atNat=0 atTgt=0` on every line means
  the gate never passes.
- `BORNSHIFT` (Info): the empirical birth shift actually applied.
- Log counters cap (SUBSHIFT 40/sweep-cycle, SUBCAND 24 total) — the
  SUBSHIFT counter resets when a new menu's ring paints (ringFresh), the
  SUBCAND one does not; a silent log can mean "cap hit", not "nothing
  happened".
