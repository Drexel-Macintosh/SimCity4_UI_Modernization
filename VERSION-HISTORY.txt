SC4UIScale 4.8.0 (2026-09-01) - 1.5x edges are one width again: the hybrid
================================================================================

THE DEFECT, in the player's words: at 1.5x, "ragged / uneven edges - some
strokes 1px, some 2px, stair-steps of different sizes, nothing smeared",
everywhere. Not text, not seams. That signature is nearest's at 3/2 and it is
arithmetic: source columns get multiplicity 2,1,2,1, so a 1px stroke renders
1px or 2px by the parity of its origin. Measured on advisor sheet 14015571
(2026-08-16): column runs 1px x106 / 2px x110; 2x is 2px x216 and 3x 3px x216,
uniform. #200 (v4.3.0) had flipped the 1.5x default from the area average
(user: "soft") to nearest. BOTH HORNS HAD NOW BEEN REJECTED ON SCREEN.

THE RUNTIME IS INNOCENT and cannot help. Blt clips and never stretches, the
DX7 driver's whole 2D blit family is stubbed, every UI pixel is a textured quad
drawn 1:1 at the art's own size, dgVoodoo is Filtering=appdriven /
Resolution=unforced, and the DLL sets no render state (the only 1.5x-only DLL
stretch is kFillSlack, <=2 px on runtime portraits). The fix lives in the art
pipeline, exactly where #200 lived.

THE ODD/EVEN THEOREM (tools/research/sharp15/theorem_check.py prints it on
synthetic strokes at every phase). A run of width w wants 1.5w pixels, an
integer only for even w:

    rule                          1px        2px       3px        4px   invented
    nearest (copy, phase-fixed)   1|2        3         4|5        6      0
    naive tie -> longer run       1          2|3       4          5|6    0
    area average / box            1+half     3(+halves) 4+half    6      many
    EDGE-CLAIM rule (copy)        1 (thin)   3         4 (thin)   6      0

A copy rule consistent for odd widths is inconsistent for even ones and vice
versa - which is why the 2026-08 lab's even_nearest moved nothing (26.1% ->
26.2% uneven). The EDGE-CLAIM rule is consistent for both: at a 2+2 tie block
across a source edge, a salient even-width run (contrasts with BOTH neighbours
by >= 48 luma, < 5 px) at half-offset owns two tie blocks and takes exactly its
left/top one (net 1.5w, exact); a salient odd-width run owns exactly one tie
block and the policy decides it (thin: gives it away, bold: takes it); a long
run or a gradient step absorbs. The first version keyed on run length alone
and found no absorber inside a bevel gradient, where every run is 1px, so it
fell back to nearest on exactly the strokes the user sees. The contrast test is
what made it work on real chrome.

A COPY RULE CANNOT HELP A CURVE. On the real 9-slice frame {1abe787d,
144161e4} plain thin/bold left cv1 at 0.35/0.32 (nearest 0.33): every tie on a
diagonal or an arc is an isolated staircase step, and the rule falls back to
nearest there by design. On an anti-aliased button they produced visible
jaggies. THE HYBRID decides per BLOCK, with no derived list for the split: a
block with a 3-of-4 majority copies; a tie that CONTINUES in the neighbouring
block along the edge (a straight edge) takes the edge-claim copy; every other
block - a staircase step, a curve, a picture - takes the key-aware 2:1 area
average. Straight chrome stays a crisp copy at one width; curves get the AA a
vector UI renders at 150%. On the frame: cv1 0.33 -> 0.16 with a third of the
box's invented colours; on the AA button it collapses to the smooth box result
instead of the jaggies.

THE KEY SET IS NEAREST'S KEY SET (shipping rule; it replaced 9 hand reverts).
The colour key is the engine's transparency and R2 holds the exact-key set to
the nearest prediction. The transparency MASK is nearest's; only the colour
inside it is the hybrid's. Where nearest says key the pixel is exact
0xFFFF00FF; where nearest says colour but the average landed on the key by
coverage, the pixel takes the key-excluded average of its block.
gate_key_integrity: PASS at 1.5/2/3 with zero exemptions added; key_near
10,251 -> 10,251 and key_moved 2,059 -> 2,059, unchanged from v4.7.2
corpus-wide.

THUMBNAILS KEEP NEAREST, AND NO PIXEL PREDICATE COULD HAVE SAID SO. Launch 1
(thin_h everywhere but even-strips, no-smooth, fine-key sheets and the 9 keyed
sheets, hand-reverted): "It all looks a lot better. Maybe the thumbnails still
don't look as sharp though." ramp_census.py and stroke_census.py over 2204
sheets: the glossy mode buttons the hybrid improved read ramp_frac 0.74-0.99
and stroke density 0.05-0.08; the lot thumbnails 0.47-0.86 and 0.08. Both are
anti-aliased art. What differs is what the picture DEPICTS - a binding fact.
So thumbnails.txt is DERIVED from the binding: every PNG the ItemIcons +
ItemIconsSub packages carry (485 TGIs, all group 6a386d26 - the exemplars'
item-icon references and the submenu icon sets). A rendered picture wants hard
pixels, and the 2x/3x block copy is the user's reference for "sharp".
Catmull-Rom and Lanczos were measured for the soft branch and rejected: at 3/2
neither is sharper than the box on photoreal art (edge_w 1.66 either way).
Launch 2: "Thumbnails are sharp."

THE PORT IS THE SAME FUNCTION, PROVEN NOT ARGUED. Upscale2x.cs UpscaleHybrid
(--hybrid thin, --thumbnails thumbnails.txt; dispatched after the even reduce

TRIGGER: a player reported a file of ours resting in
  C:\Program Files (x86)\Steam\steamapps\common\SimCity 4 Deluxe\Plugins
while the shipped README promised "after a clean exit there is nothing there to
delete". Reproduced in one measurement: FontStyle.ini.x1-disabled, 23,016 bytes.

THE INSTALLER WAS INNOCENT, and checking that first mattered. The v4.5.9 bundle
holds only the three tier sources and the empty z_SC4UIScale_FontStyle.ini
placeholder; Install.ps1 copies only what the bundle holds. The #182 packaging

WHAT I GOT WRONG, TWICE, AND THE USER GOT RIGHT THREE TIMES.
Asked why the file could not simply use a different name, I answered that the
game probes two FIXED PATHS - true - and concluded the FILENAME was therefore
fixed. Those are different claims. The filename is four imm32 operands:

    0x0044DC98  68 D5 6D A8 00   push 0x00A86DD5   ; end
    0x0044DC9D  68 C8 6D A8 00   push 0x00A86DC8   ; begin
    0x0044DCD1  68 D5 6D A8 00   push 0x00A86DD5   ; end
    0x0044DCD6  68 C8 6D A8 00   push 0x00A86DC8   ; begin

0xA86DD5 - 0xA86DC8 = 13 = strlen("FontStyle.ini"), and neither address is
referenced anywhere else in .text. Repointing them is the same push-imm32 patch
a dozen families in CodePatches.cpp already perform. I measured one thing and
concluded about another, then repeated it instead of re-checking.

FONTNAME (new): all four operands repointed at z_SC4UIScale_FontStyle.ini, at
both probe paths. All four are verified before any is written - a half-redirect
would hand the concatenation a begin from one string and an end from another, a
length computed across unrelated memory. On refusal ScaleTier falls back to the
stock name, so a failed patch cannot strand a font under a name nothing reads.
Armed before SyncStaticLayers, which is what decides the filename.

CONSEQUENCES, each measured:
 * The player's FontStyle.ini is never read, overwritten, backed up or restored.
   The whole .user-original mechanism becomes UNNECESSARY rather than carefully
   handled - and it had misfired twice in two days, once mistaking our own
   stamped file for the player's and "restoring" it.
 * Stock tier now DELETES our font instead of renaming it to .x1-disabled. The
   old path left 23 KB in Program Files after every clean exit, forever.
 * A crash is now cheap. The redirect lives in the LOADED IMAGE ONLY - verified
   by reading all four operands back out of the exe on disk, where they still
   hold the stock pointers. Without our DLL there is no redirect, so a stranded
   copy is inert. Previously a stranded FontStyle.ini kept the enlarged font
   applied forever, even after uninstalling.
 * Install.ps1 -Uninstall now sweeps the game folder, which it had never looked
   at - removing only what it can PROVE is ours (our filename, or a stock-named
   leftover carrying our generated-file header) and reporting anything else.
 * The font we write carries a header naming the mod and saying it is safe to
   delete. It also improves our own ownership test, which was byte-identity
   against a tier source and would stop recognising anything the moment a
   source was regenerated.

NEW GATE: _tests/Test-GameFolderClean.ps1. Nothing in the regression net had

2026-08-21  v4.0.1   TWO REAL-USER BUGS FROM THE FIRST PUBLIC RELEASE, BOTH
                     CLOSED THE SAME DAY THEY WERE REPORTED

  The first external install (a heavily-modded sc4pac-managed Plugins tree:
  45,945 files, 14.1 GB, "150-mods"/"050-load-first" structure) hit two
  defects neither of which any dev-machine install was large enough to
  reach. The user's own log named the first one directly.

  1. ICON COVERAGE WAS TRIPLE-CAPPED, AND EVERY CAP WAS SIZED FOR A SMALL
  INSTALL. IconSynth::ScanState::ours[]/theirs[] were fixed uint32_t[4096]
  arrays; the fix queue gFixList[] and the reference-hold array gHold[]
  were both fixed at 512. On this install the scan hit its cap and
  DROPPED 6,619 third-party icon TGIs outright (logged loudly: "TGI CAP
  HIT ... UNCOVERED is a LOWER BOUND"), and of the 4,048 icons it DID
  count as uncovered, only the first 512 could ever be queued for
  correction - the remaining 3,536+ stayed rendered at 1x forever, no
  matter how long the session ran. Visible as icons that "render doubled
  and vanishes on hover", per the scan's own diagnostic text.

  Cure: all three arrays became growable (U32List/PtrList, realloc-doubling
  from a 1024-entry floor, freed only where their lifetime actually ends -
  gFixList and gHold are process-lifetime and never freed, matching their
  existing "held on purpose" design). Nothing caps them now; the scan
  reports an EXACT count instead of a lower bound, and every icon it finds
  is queued and attempted. Same standing law this codebase already names
  in a dozen other places (⭐108: "a patch that cannot EXPRESS its value
  must REFUSE or WIDEN, never silently truncate") - this was the same
  defect shape, just never triggered until an install this size existed.

  Removed as dead once nothing can overflow: the "TGI CAP HIT" log branch,
  gFixTruncated and its "(LIST TRUNCATED at 512 - more remain)" suffix, the
  gHoldN>=kHoldMax skip gate. Every remaining log line is still accurate,
  just no longer hedged with "lower bound" language it no longer needs.

  2. SC4PAC CANNOT UNINSTALL A FILE THE DLL GENERATES. Reported by an
  sc4pac maintainer: FontStyle.ini is never shipped in any package - the
  DLL creates it at first boot by copying one of the three tier sources
  over it - so a package manager has no record of it and uninstalling the
  mod through sc4pac leaves it orphaned. No DLL change: SyncFont's own
  #115/#118 preservation logic already treats a non-matching live file
  safely (backs it up once as .user-original, then overwrites it with the
  real tier font in the same pass), so an EMPTY file behaves exactly like
  no file at all. Build-Dist.ps1 now writes a zero-byte FontStyle.ini into
  the bundle's Plugins\ root, asserted empty before it ships, so a package
  manager can track and remove it like any other installed file.

  Both fixes are packaging/runtime only - no ini keys, no new Settings
  fields, no dat changes. Full gate set green, DatIntegrity green, rebuilt
  and re-deployed on the dev machine; public repo re-exported and pushed as
  v4.0.1.

  bumped the version and ran the export but the ledger habit lapsed at the
  exact moment it mattered most. Backfilled immediately below.
