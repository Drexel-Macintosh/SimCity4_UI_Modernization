A day with real wins (#193, #190, the 1x baseline, the tier tooling) and **five

⭐ **LAW: STATIC EVIDENCE PROVES WHAT AN ADDRESS DOES. IT NEVER PROVES THAT
ADDRESS IS THE THING ON SCREEN.** The only test that does is changing it and
looking, and that test costs one deploy. When three attempts in a row run clean
and change nothing, **the fault is in the identification step** and more
disassembly cannot fix it.

⭐ **LAW: RUN THE SDK-BOUNDARY TRIAGE BEFORE THE FIRST PATCH.**
`reference-sc4-ui-sdk-boundary` already carried it and says *"apply before
spending a session"*: (a) never a window in a full-depth dump, (b) no art in any
dat, (c) overlays the 3D view. One ten-second `LiveDumpMs=1000` launch answered
it — 37 dumps, **0 new windows** while the marker was up. That single
measurement retires the entire window toolkit and would have prevented patches
1–4.

⭐ **LAW: READ OUR OWN UNKNOWNS REGISTER FIRST.**
`research/UNKNOWNS-AND-NEXT-TARGETS.md` **row 20** is literally *"MySim head
bubble + aircraft landing ring"* — #191 — scored and annotated *"Free if #8 is
done"*, where **row 8** is *"the other six dispatch-indicator categories
(settles a printed contradiction)"*. **Row 18** is *"the TagKind sprite's
literal size constant — continue `0x00510690` past `0x5106E7`"*. The register
named the target, the method, and warned that a printed contradiction was in
play — before any of it was spent. It was not opened all day.

## THE GREP LESSONS

⭐ **A UNIQUE ANCHOR PROVES THE TEXT IS UNIQUE, NOT THAT IT IS IN THE RIGHT
CONTAINER.** `0x48E945B4` was added "to `kNeverScaleIds`" using an anchor line
that IS unique in `UiSpike.cpp` — and lives in **`kAlwaysScaleCityIds`**. The id
went onto the FORCE-SCALE list by the edit written to protect it, so the marker
was scaled *because of* the fix. Two later sessions then invented mechanisms to
explain a null whose cause was that the change had never been made. **Verify
placement by LINE NUMBER against the enclosing array's bounds.** Every list of
hex ids looks alike in a diff.

⭐ **WHEN A FIX APPEARS INERT, RE-READ THE FILE BEFORE THEORISING.** "The edit
did not land where I think it did" outranks every subtler explanation and is one
grep to rule out.

⛔ **A `.rdata` SWEEP IS BLIND TO INLINE IMMEDIATES** (standing law 99) — and
its sibling this session: **reading ONE branch tells you where that branch GOES,
never who ARRIVES.** `0x0046CCB9` looked like the else of `cmp [esi+4],4` and is
category-3 ONLY; categories 3 and 4 *merge* at `0x46CB52` and split later. Only
an exhaustive inbound-edge enumeration showed it.

⚠ **A COMMENT CAN BREAK A GATE.** An eight-line comment inserted between
`(*count)++` and its `SetW/SetH` pushed three mutations 14/15/19 lines apart and
failed `Test-MutationCountInvariant.py` — the #117 crash-killer signal gate. Run
the gates after documentation-only edits.

## THE INSTRUMENT LESSONS

⭐ **A FETCH PROBE CANNOT FIND A CACHED CONSUMER.** `ARTFETCH` (hook on the
resource fetch) named the portrait **loader** — a preload at `0x00775239` — but
the marker draws from the registry and never re-fetches, so the hook could not
see the draw *by construction*. Before arming an instrument, ask **what it hooks
and whether the target passes through that point every time or only once**.

⭐ **AN INSTRUMENT SCOPED TO THE WRONG CHANNEL RETURNS AN HONEST NULL.**
`SEATPROBE` fires only inside `BmpCtxBltThunk` for `GZWinBMP` windows under
`kBmpxCityRoots`/`kBmpxDialogRoots`. The marker is renderer-world, so its
silence proves nothing. Its 24-row quota was also **shared**, and one window
(`0x48E945B4`) ate all 24 within 400ms — so every past hover investigation was a
filtered null. Now per-id.

⭐ **STATE THE POSITIVE CONTROL WITH EVERY NULL.** The live-dump null is
trustworthy *because* the same capture shows the Select-A-Sim grid appearing in
exactly one tick (88 transient ids). Without that, "no new windows" would be
worthless.

## THE ARITHMETIC LESSONS

⭐ **A DEFAULT THAT IS NOT THE IDENTITY TURNS "NOT YET KNOWN" INTO A CONFIDENT
WRONG ANSWER.** `gTierF = 2.0f`, assigned at only two sites (both scaling paths)
and read at **97**. At tier 1 it kept its initialiser, so the 1x baseline was
never inert — sub-flyouts were born `x2.00` inside a 1x layout. At 1.5x/3x any
hook firing before those two functions silently used 2.0. Identity is `1.0f`,
and the mirror is now pushed **unconditionally** where the tier is resolved.

⭐ **A DECISION THAT DEPENDS ONLY ON THE FACTOR MUST NEVER LIVE INSIDE A BRANCH
THAT ASKS HOW THE FACTOR WAS CHOSEN.** The "Tier 1 = TRUE stock, every subsystem
off" block sat inside `if (spikeAutoScale)`, and taking a 1x reference sets
`AutoScale=0` — so the whole sweep ran at f=1.00 (529 windows) and handed the
sub-flyout strip `item fields x2`. **Third instance of this exact shape in one
function** (#149, #182 are recorded in its own comments).

⭐ **STAGING BIGGER ART CAN BREAK A CONSUMER THAT HARD-CODES A POWER-OF-TWO
TEXTURE SIDE.** #190 staged 36x41 → 72x82, crossing the 64→128 boundary, which
halved the UVs of anything dividing by a baked-in `64`. The break appears **only
at the tier that crosses the boundary** (1.5x fine, 2x not), which reads as a
tier mystery rather than an art change. Ask **who divides by its size**.

⭐ **ART REACHABLE + GEOMETRY UNREACHABLE IS ITS OWN CATEGORY.** The SDK-boundary
triage assumes in-or-out. The Move In marker is (a) never a window, (c) overlays
the 3D view, but (b) its art **is** a dat portrait we stage. Staging bigger art
for such an element changes nothing on screen and looks like the staging failed.

⭐ **A REPAIR THAT READS THE STATE IT REPAIRS MUST BE CORRECT ON THE BROKEN
STATE.** The armed-tier snapshot scanned the disk first-match — which works only
while exactly one tier is armed, and the bug it fixes leaves two. It picked 2x on
a 3x install and disarmed the correct tier. Now it reads the DLL's own log.

## THE PROCESS LESSONS

⭐ **PRESENCE IS NOT ARMING.** Every dat gate asked "is the package present?"
CsiIcons was present at all three tiers, correct sizes, and the **1.5x** one was
live on a 2x install. The runtime `SyncDat` then repairs the disk at launch,
erasing the evidence before any log is read. **A defect that self-heals before it
can be observed is the hardest kind to see.**

⭐ **A CAUTION WRITTEN ABOUT ONE LEVER GOES STALE THE MOMENT A SECOND LEVER
FIRES ON THE SAME OBJECT.** "Do not patch the else branch, it would resize
unrelated indicators" was correct when only the icon scaled, and became the cause
of the defect once the shared pin quad started scaling too.

⭐ **A SKIP LIST SKIPS THE FUNCTION, NOT THE LINE.** The panel loop's
`IsNeverScaleId` does `continue`, which skips the whole `ScalePanelRoot` call —
and the child walk lives inside it.

⭐ **WHEN EXCLUDING AN ID, CHECK FOR A TWIN IN THE SAME SCRIPT.** `0x27DF05BE`
and `0x27DF05BF` share a script, area and image; only BF was listed, so the sweep
scaled one and froze the other.

⭐ **A WRONG NAME IN OUR OWN SOURCE IS A SEARCH-BLOCKER.** `0x48E945B4` is
commented "the U-Drive-It mission marker"; it is the **right-drag anchor ring**
(`ScrollWin::GZOnMouseDownR`). Every audit keyed on that label looked at the
wrong widget and returned an honest null. **#193 and #197 were one defect.**

⭐ **"WRITTEN BUT NEVER APPLIED" IS NOT A SAFE RESTING STATE.**
`fix_ringguards.py` sat in the scratchpad all session; compiling it showed it
fails two ways, one guard site is dead code, and the hazard is a single latent
1.5x path. A patch script that has never been compiled is a hypothesis.

⭐ **READ THE WHOLE MEASUREMENT BEFORE ACTING ON ITS FIRST PARAGRAPH.** The
report that named `0x0046CB09` in section 1 disqualified it in section 9. It was
patched off section 1.

⭐ **THE USER OBSERVES, I MEASURE.** Asking them to paste a log filters the
evidence through a grep I chose — several findings came from lines adjacent to
the ones I would have asked for. Screenshots and "this looks wrong" from them;
every byte on disk from me.
